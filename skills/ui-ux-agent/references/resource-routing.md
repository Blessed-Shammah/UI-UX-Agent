# Choose a foundation, then make it belong to the product

## Use the planner as a decision aid

When the npm CLI is available, use `ui-ux-agent inspect --project <app>` and `ui-ux-agent plan --brief <brief.json> --project <app> --json`. The planner reads bounded project markers and ranks a dated resource registry. It does not see a live preview, browse current licenses, or decide visual quality. The host agent must do those things with its available tools.

For a copied skill without the CLI, inspect the project yourself. The installer includes `resources/routing.json` within this skill folder. In the source repository the registry is at the repository's `resources/routing.json`. Read only relevant entries, compare the conditions below, and record the choice.

## Decision order

1. **Existing system:** extend working project components and tokens first. A missing section does not justify installing a second competing component system. Confirm the actual app folder in a monorepo.
2. **Platform and stack:** React blocks are not native mobile or WPF controls, and do not drop into Vue/Svelte unchanged. Electron/Tauri content can use compatible web components, but still needs desktop behavior.
3. **Task:** marketing needs credible persuasion and a product demonstration; operational tools need forms, queues, tables, detail views, and recovery. Do not choose by visual fashion alone.
4. **Cost and distribution:** inspect the actual free subset and exact item's license. An end-product license is different from permission to redistribute a kit. No copying paid templates into an open-source repository.
5. **Visual fit and effort:** inspect representative preview/source, content rhythm, narrow layout, type, token compatibility, and adaptation cost. Choose one main system and supporting pieces only where there is a named gap.

## Useful routes

| Need | Candidates to inspect | Reason and boundary |
| --- | --- | --- |
| React product landing page | Tailark OSS with the project's shadcn foundation | Marketing composition and reusable blocks; distinguish OSS from paid offerings and align primitive bases |
| React working application | Existing system or shadcn/ui; TailAdmin free when a full dashboard actually fits | Forms, navigation, queues, states; avoid decorative dashboard widgets |
| HTML marketing page | Landwind, semantic HTML, selected PrebuiltUI items | Compare integration effort and exact item rights; do not add React to an HTML app for one section |
| Clean visual/component exploration | PrebuiltUI's clean-UI search and official component pages | Treat each result as an item needing stack, price, license, and live inspection |
| Cross-framework Tailwind components | daisyUI where compatible | Semantic classes/theme roles; interaction behavior still needs implementation |
| Vue/Svelte application | Current system, shadcn-vue/shadcn-svelte, compatible daisyUI | Match the actual framework; verify ports' licenses and versions |
| Bootstrap operations tool | Tabler when already aligned with Bootstrap | Dense practical layouts; do not mix Bootstrap with a mature conflicting foundation |
| Expressive React moment | Selected React Bits or Magic UI items | Optional enhancement only when the brief calls for it; verify performance, rights, and reduced motion |
| Native mobile/desktop | The chosen toolkit and OS conventions | Web libraries can inform composition, but do not supply compatible native controls |

This table is not an exhaustive list. Search additional official sources when none fits, rather than forcing a named library into every brief. A custom semantic layout is a valid choice.

## Inspect, integrate, and verify

For each shortlisted source, inspect its actual page/component, code, license, dependencies, and behavior. Keep a small decision record: chosen source and revision, role in the product, reasons, rejected alternatives, modifications, notices, and remaining checks. Prefer reading current official installation instructions to guessing registry commands or package names.

Do not return a link collection as the finished design work. After selecting the foundation, implement the user's product: meaningful content, coordinated tokens/type/spacing, coherent component states, the primary journey, responsive/platform behavior, and a rendered review. Use the quality gates and revise the highest-impact issues before handing it back.

If browsing is absent, report the shortlist as provisional, use supplied/project sources, and mark live checks unverified. If repeated attempts fail, change the unsuitable foundation or composition with an explicit reason; do not cycle through unrelated libraries.
